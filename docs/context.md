# HelpDesk Copilot — Project Context

## What We Are Building

We are building **HelpDesk Copilot**, a production-oriented Agentic AI customer-support platform as part of a three-stage Agent Engineering project.

The goal is NOT to build a simple chatbot.

The system should eventually be able to:

* Understand customer-support requests
* Decide what actions are required
* Call backend tools
* Observe tool results
* Continue reasoning/actions when necessary
* Validate tool inputs
* Enforce safety policies in code
* Recover from tool failures
* Maintain an observable execution trace
* Plan multi-step tasks
* Reflect on generated answers
* Pause for human approval before risky actions
* Resume correctly after being paused
* Route simple requests to deterministic workflows
* Coordinate multiple specialist agents
* Perform multi-source research
* Eventually support voice interaction

The project has **three builds**, each extending the previous one.

---

# Build 1 — Single Agent

Build 1 is the foundation.

### Technology

* Backend: Node.js + Express
* Frontend: React or Next.js
* Database: MongoDB + Mongoose
* Cache/state: Redis
* LLM: provider with native tool calling
* Vector store: ChromaDB
* Streaming: SSE

### Core Agent Loop

We must implement the agent loop ourselves.

Do NOT use a black-box framework abstraction such as:

```text
agent.run()
```

The loop should conceptually work as:

```text
User Request
     ↓
Send conversation + tool definitions to LLM
     ↓
LLM returns tool call OR final answer
     ↓
If tool call:
    validate arguments
    execute tool
    record result
    append result to conversation
    call LLM again
     ↓
If final answer:
    stream response
    finish
```

The loop must eventually support:

* Maximum iteration cap
* Token budget
* Graceful termination
* Persistent execution trace
* Tool errors without crashing the agent

# Build 1 Tools

The system should eventually contain at least these tools:

1. `searchKnowledgeBase(query)`
2. `getCustomer(email)`
3. `getOrders(customerId, limit)`
4. `getInvoices(customerId)`
5. `checkRefundEligibility(orderId)`
6. `issueRefund(orderId, amount, reason)`
7. `applyAccountCredit(customerId, amount)`
8. `escalateToHuman(reason, priority)`

Every tool must have:

* JSON schema
* Input validation
* Safe argument handling
* Structured error responses

Never blindly trust arguments generated by the LLM.

Example:

```json
{
  "error": "customer_not_found",
  "message": "No customer exists for this email"
}
```

Tool failures should be returned to the agent so that it can reason about them.

# Safety Requirements

Safety is a major part of this project.

Important rule:

**Safety restrictions must be enforced in application code, not only in prompts.**

For example, if refunds above a certain amount are prohibited/autonomously restricted, the `issueRefund` function itself must enforce the limit.

A system prompt saying:

```text
Never refund more than $500
```

is NOT sufficient.

Write operations must also have appropriate confirmation/approval behavior.

The system should demonstrate failure cases such as:

* Out-of-policy refund
* Tool error
* Iteration limit reached
* Invalid tool arguments

# RAG / Knowledge Base

The system will contain customer-support documentation and policy documents in ChromaDB.

The `searchKnowledgeBase()` tool retrieves relevant information.

Policy-related answers must be grounded in retrieved documents and provide citations.

If the available evidence does not support an answer, the agent should say that it cannot determine the answer instead of inventing a policy.

# Observability

Every agent run should eventually produce an inspectable trace.

A trace should contain information such as:

```text
run ID
iteration
LLM request
tool name
tool arguments
tool result
success/failure
duration
token usage
```

The frontend should eventually expose this trace to the user/operator.

The backend will eventually stream agent activity through SSE.

Expected event categories include:

```text

```

The frontend should show live activity rather than only displaying a loading spinner.

# Build 2 — Planning, Reflection & Human-in-the-Loop

Build 2 extends Build 1.

For multi-step requests, the agent should create an explicit plan before acting.

Example:

```text
1. Find customer
2. Retrieve invoice history
3. Identify duplicate
4. Check refund eligibility
5. Request approval if necessary
6. Issue refund
7. Explain result
```

If a step produces an unexpected result, the agent should revise the remaining plan.

Before returning a final response, a reflection pass should evaluate:

* Did we answer the actual question?
* Are claims grounded in tool results/documents?
* Is the tone appropriate?
* Did we expose internal information?

Reflection should have a strict revision cap.

Build 2 also introduces Human-in-the-Loop approval.

Different actions have different autonomy levels:

```text
Read-only
    → autonomous

Low-risk writes within policy
    → autonomous + logged

High-risk/large writes
    → human approval

Legal/security/account deletion
    → always human
```

A paused agent must persist its state and survive a server restart.

The approval system should support:

* Approve
* Reject
* Modify

Resumption must be idempotent so that approving twice cannot execute an action twice.

Build 2 also introduces routing:

```text
Deterministic workflow
        ↓
Guided agent
        ↓
Autonomous agent
```

Not every request should use an autonomous agent.

# Build 3 — Multi-Agent, Research & Voice

Build 3 introduces specialist agents and a coordinator.

Architecture:

```text
                Coordinator
               /     |      \
              ↓      ↓       ↓
          Billing  Technical Account
           Agent     Agent    Agent
```

There will also be a Research Agent for open-ended questions.

Each specialist should have:

* Its own system prompt
* Its own tool subset
* Its own knowledge base
* Clearly defined handoff contract

The coordinator should be able to handle requests involving multiple specialists.

Agent-to-agent loops must be prevented with delegation limits.

---

# Research Agent

The Research Agent should:

1. Decompose a question
2. Investigate sub-questions
3. Query multiple sources
4. Run structured database analysis where appropriate
5. Synthesize findings
6. Cite sources
7. Report confidence
8. Explicitly state uncertainty

It must not fabricate information when evidence is unavailable.

---

# Voice

The final system should expose the same agent core through voice:

```text
Browser microphone
       ↓
STT
       ↓
Agent core
       ↓
TTS
       ↓
Audio playback
```

Voice should support streaming, interruptions/barge-in, tool execution progress, and a design for approval-required actions.

Do NOT create a separate voice-only agent implementation. Reuse the same core agent architecture.
